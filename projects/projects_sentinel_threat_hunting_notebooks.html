Threat Hunting Notebook Suite for Microsoft Sentinel & XDR

A Python notebook layer for Azure Machine Learning that connects to Microsoft Sentinel, enriches indicators through three threat-intelligence sources, reconstructs Email → Endpoint → Cloud kill chains across Microsoft Defender products, and detects anomalous endpoint behaviour with an explainable Isolation Forest model.

A security team running a proof of concept on an Azure development tenant wanted analysts to hunt threats in Jupyter notebooks instead of pivoting by hand between Defender for Office 365, Defender for Endpoint and Defender for Cloud Apps. The client owned the security side — Sentinel configuration, data connectors and every KQL query — and needed someone to build the entire Python layer on top of it.

I delivered three notebooks against a detailed cell-by-cell specification with formal acceptance criteria. NB-00 is a shared library imported by every other notebook: Sentinel connection, a guarded KQL runner, incident creation and a prioritised IOC-enrichment chain (MISP → Microsoft Threat Intelligence → VirusTotal). NB-06 correlates a suspicious email with the click, the process it started and the cloud activity that followed, then maps each step to MITRE ATT&CK. NB-01 learns normal endpoint behaviour with Isolation Forest and explains every flagged account with SHAP.

My service-principal access was not enough to execute cells against the tenant myself, so the client ran each milestone end-to-end in Azure ML. That shaped the engineering: every notebook had to run correctly on the first attempt in an environment I could not reach — with sparse data, a threat-intel platform that was not deployed yet, and query schemas that arrived during the project.

Outcome: three integration-ready notebooks delivered in two milestones, validated by the client in Azure ML. Analysts change parameters in a single cell, review interactive kill-chain timelines and anomaly tables, and escalate confirmed findings to Sentinel incidents in one step.

Overview

In a Microsoft security stack the evidence of a single attack is split across several products. The phishing email is in Defender for Office 365, the click is in Safe Links, the malicious process is in Defender for Endpoint, and the data access that follows is in Defender for Cloud Apps. Connecting them means running a query in each console and matching accounts and timestamps by hand.

The notebook suite automates that pivot inside Azure Machine Learning. Every notebook begins by loading NB-00, so authentication, KQL execution, threat-intel enrichment and incident creation are implemented once and reused. Notebooks NB-06 and NB-01 contain only analysis logic: the brief required that no authentication or query-provider code appear in them, and they are verified by searching for those class names.

Each analysis notebook follows the same analyst workflow. All tunable parameters — look-back window, correlation tolerance, contamination rate, thresholds — sit in the first cell. The notebook loads data, builds a result, shows it as an interactive chart or a styled table, and ends with a review cell where the analyst lists confirmed accounts and adds notes. The final cell turns each confirmed finding into a Sentinel incident with the evidence written into its description.

The development tenant contained very little real security data. The brief was explicit that empty stages are not defects and that what is assessed is code quality, error handling and correct join logic. The code therefore treats “no data” as a normal state at every step rather than as an exception.

Cross-Domain Kill Chain (NB-06)

NB-06 starts from suspicious emails and follows what happened to the same account next. Each stage is pulled with its own KQL query and linked to the previous one only if it occurred within a configurable time window (60 minutes by default).

Stage Product Table Linked by MITRE ATT&CK
1 · Suspicious email Defender for Office 365 EmailEvents Delivered, not blocked or junked T1566 Phishing
2 · URL click Safe Links UrlClickEvents Same NetworkMessageId as a stage-1 email T1204 User Execution
3 · Device process Defender for Endpoint DeviceProcessEvents Same account, started within the window after a click T1059 Command Interpreter
4 · Cloud activity Defender for Cloud Apps CloudAppEvents Same account, within the window after a linked process T1530 Data from Cloud Storage

All linked events are combined into one kill-chain table with a fixed schema — account, stage, label, timestamp, readable description, MITRE stage and technique, and the original row. Accounts that match fewer stages than MIN_STAGE_THRESHOLD are filtered out, and a summary shows stages matched, first seen and last seen per account. Each remaining account gets its own interactive timeline, colour-coded by stage, with the event description and technique on hover.

run_kql() is the only path to data in the suite. It defaults to the last 24 hours, raises a readable ValueError when the requested window is longer than the allowed maximum, and returns an empty DataFrame on zero results or a failed query instead of raising. Every stage of every notebook can therefore be written as “load, then check if empty”, without its own error handling around the data source.

enrich_ioc() asks the sources in a fixed order and stops at the first match. MISP is the client's own intelligence and goes first. Microsoft Threat Intelligence is queried through client-provided KQL templates, with IOC values quoted and escaped before formatting. VirusTotal is called only when neither returns anything. The VirusTotal function is wrapped in joblib.Memory, so a repeated lookup is answered from disk in under 50 ms and does not spend the free-tier quota. Each source failure is caught inside its own step, so one unavailable service never hides the others.

In NB-06 every stage DataFrame is normalised before it is used: missing expected columns are added as empty, timestamps are parsed as UTC with invalid values coerced, and account names are lower-cased so that the same user matches across products. Both sides of every merge_asof() are cleaned of missing keys and sorted by timestamp immediately before the join — merge_asof() does not fail on unsorted input, it silently returns wrong matches.

NB-01 builds one feature row per device and account: process count, distinct process names, average command-line length, network events, distinct remote IPs, share of connections to high ports, logon count, share of activity outside working hours and number of devices per account. Missing tables mean zero activity, not unknown. Features are standardised, the model is trained only if the data-volume guard allows it, and decision scores are rescaled to a 0–1 risk score. SHAP values for each flagged account are turned into its three strongest reasons, each compared with the population average.

Incident descriptions are generated from the analysis rather than written by hand: stages observed, first and last event, MITRE techniques, MISP correlation result, a timestamped event list and the analyst's notes for kill chains; risk score, SHAP reasons and all feature values for anomalies.

Architecture / Workflow

  • Step 1: The analyst opens NB-06 or NB-01 in Azure ML and adjusts parameters in the first cell only.
  • Step 2: The notebook loads NB-00, which reads credentials from the environment and connects to the Sentinel workspace.
  • Step 3: Client-provided KQL queries are executed through run_kql() with a time window derived from the look-back parameter.
  • Step 4: NB-06 links email, click, process and cloud events per account; NB-01 builds behavioural features and scores them with Isolation Forest.
  • Step 5: Results are enriched with MITRE mapping, MISP campaign data or SHAP explanations.
  • Step 6: The analyst reviews interactive timelines or the colour-coded anomaly table and lists confirmed findings.
  • Step 7: The last cell creates a Sentinel incident for each confirmed finding, with the evidence in its description.

Challenges & Solutions

  • Challenge: The specification's example join used direction='forward' with process events on the left. In merge_asof() that links each process to a click that happens after it — the reverse of the attack sequence.
    Solution: Kept the process (and cloud) events on the left and used direction='backward', so each event is matched to the most recent click (or process) of the same account within the tolerance window; unmatched rows are dropped.
    Result: The acceptance check holds: a process 30 minutes after a click is linked, one 90 minutes after is not, and nothing is linked backwards in time.
  • Challenge: I could not execute cells against the tenant myself — the client ran every milestone in Azure ML — so a failure would only surface after a full review round.
    Solution: Wrote smoke tests that print PASS per acceptance criterion, kept every cell runnable with placeholder or empty queries, and isolated client-specific values in environment variables and query modules.
    Result: The client could check each criterion directly from cell output, and integrating the validated live queries later required only schema adjustments, not rewrites.
  • Challenge: The development tenant had little data; any stage could come back empty, and an empty stage must not stop the ones after it.
    Solution: Normalised every stage to its expected schema and added fallbacks: with no clicks, processes are linked directly to email recipients; with no linked processes, cloud events are kept for accounts already seen upstream.
    Result: All stages run whichever query returns nothing, and the kill-chain table always has its full column set, even when empty.
  • Challenge: MISP was not deployed when development started, but the code for it had to be ready and the notebooks could never crash because of it.
    Solution: A dedicated MISPUnavailableError, raised when credentials are missing or the server is unreachable, with a module-level flag so the warning is printed only once per session.
    Result: MISP turns on automatically once its URL and key are set; until then enrichment and campaign correlation continue with the other sources and a single message.
  • Challenge: The VirusTotal free tier allows only a few requests per minute, and analysts often enrich the same indicators repeatedly.
    Solution: VirusTotal is the last source in the chain and its lookups are cached on disk with joblib.
    Result: A repeated lookup returns in under 50 ms without spending quota.
  • Challenge: The shared KQL runner caps queries at seven days by default, while anomaly detection needs a 14-day behavioural baseline.
    Solution: NB-01 passes its look-back as the allowed maximum explicitly instead of weakening the default guard.
    Result: Accidental wide queries stay blocked across the suite, while the model gets the baseline it needs.
  • Challenge: On sparse telemetry Isolation Forest flags almost everything or nothing, which would mislead an analyst.
    Solution: A data-volume guard runs before training: below 50 accounts the notebook stops with an explanation, below 200 it warns. Later cells check whether a model exists, and a SHAP failure is caught so the results table still renders.
    Result: The notebook never presents results from a model trained on too little data.
  • Challenge: The project had strict confidentiality rules: credentials provided by the client, a client-owned repository, and compute that could be recycled without warning.
    Solution: All secrets come from environment variables, configuration files and caches are excluded from Git, and work was committed after each working cell.
    Result: 38 commits with a clear per-cell history and no credentials or workspace identifiers in the code.

Result

The client received a working threat-hunting notebook suite on its Azure development tenant: one shared library and two analysis notebooks that analysts operate through parameters and review cells, without writing Python. Investigations that previously required pivoting across three Defender consoles become a single run that ends in an interactive timeline and, if confirmed, a Sentinel incident.

Each notebook stays usable when data is missing — no events, no MISP, no VirusTotal key, too little telemetry to train — and always explains what it skipped instead of failing.

From an engineering perspective, the project shows how I work in security tooling: building to a strict specification and acceptance criteria, questioning the specification where it was wrong, writing code that runs correctly in an environment I could not access directly, and treating partial failure and sparse data as normal operating conditions.
